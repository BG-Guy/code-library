The "What we do" section from pinevalleydigital.com, packaged as a drop-in component. No dependencies: one JS file plus one stylesheet. Its defining idea is that **every moving thing shares one spring clock**, so growth, shrink and slide stay in step even when you interrupt them mid-flight.

**How it works**

1. **One spring engine, not CSS transitions.** The row's `translateX` and *every* card's width are `SpringValue` objects advanced together in a single `requestAnimationFrame` loop. Because each carries its velocity through a change of target, interrupting a half-finished animation keeps its momentum instead of restarting it. `advance()` integrates in fixed 1/240s sub-steps, so the motion is identical at 60Hz and 144Hz. Two presets: `LAYOUT_SPRING` is SwiftUI's default (0.55s response, 0.825 damping, ~1% overshoot) for opening and closing; `SCROLL_SPRING` is quicker and bouncier for following the wheel and springing back from a stretched end.
2. **Widths change, content does not reflow.** Each card's body is laid out at the *open* width and clipped, pinned to its left edge. A growing card therefore reveals its content rather than re-wrapping it every frame — the thing that normally makes this kind of animation look cheap. The art layer is centred and fixed at the open width for the same reason, so it is revealed, not stretched.
3. **Wheel ownership is decided per gesture, not per event.** This is the subtle part. A run of wheel events with no pause longer than `GESTURE_GAP` counts as one gesture, and `ownerFor()` decides *once*, on its first event, whether the row, the page-glide or the page handles it. That matches how browsers treat nested scrolling: once the first event of a gesture has gone to the page, the rest cannot be taken back. The practical effect is that running the row into its end does not then jerk the page mid-swipe — the page only moves on your *next* scroll.
4. **Rubber banding.** Past either end the row stretches with diminishing returns (`rubber()`, the iOS curve), capped at `MAX_OVERSCROLL`, and the stretch keeps relaxing between events on a `STRETCH_RELAX` time constant — so a trackpad's dying momentum lets it settle back rather than pinning it open. The scrollbar thumb squashes while stretched, as iOS's does.
5. **The corner notch.** The open card's arrow link sits in a notch cut *into* the card, with the ink border and hard shadow following the cut. That only works because the link lives outside the card's clipping layer, in `.ecr-socket`, while everything else is inside `.ecr-clip`.
6. **Animated lines per card.** One canvas is moved into whichever card is open and reconfigured for it. `linesFor(i)` derives tilt, spread, pinch point, ripple, pace and lead colour from a hash of the card index, so no two cards animate alike and each looks the same every time it opens. It only draws while a card is open and the row is on screen.
7. **Accessibility is structural.** Each card has two halves and exactly one is live: opening a card marks the pill `inert` and un-inerts the body, so the dormant half leaves both the tab order and the accessibility tree. Focus is moved deliberately rather than abandoned on an inert node, tabbing to an off-screen pill slides it into view, and the scrollbar is a real `role="scrollbar"` with a live `aria-valuenow`.

**Using it in this project**

The stylesheet is **not** injected by the component — load `expandingCardRow.css` once yourself. It is a separate file here rather than inlined into a comment at the top of the JS, because its own 32 comment blocks would close a wrapping block comment early.

Match your site by setting these on the section: `--ecr-ink`, `--ecr-bg` (must equal the section's background, since the notch is cut in that colour), `--ecr-light`, `--ecr-accent`, `--ecr-accent-2`, `--ecr-font-display`, and `--ecr-nav-h` if the page has a fixed header. Card colours are themes — `.ecr-theme-<name>` sets two gradient stops and two highlights, and you pass the names in the `themes` option.

The original is TypeScript. The code above is that source with the type annotations removed, which the component's own notes call for in a plain-JS project; the verbatim `.ts` files sit beside it in this snippet's folder, along with `example.ts` showing plain-JS and React mounting. `fillScreen` defaults to true, which makes the section exactly one screen tall and glides the page into it — the preview below passes `false`, since a one-screen section cannot show itself inside a short frame. It assumes the page scrolls on the window, not inside a scrolling element.
